### 7. Idempotency Clarification (from answer 3a)

You said "i dont understand" about the idempotency approach. Let me simplify:

The question is: **what happens if you run the seed script twice?** Three options:

1. **Delete-and-recreate**: The script looks for a user with email `seed-test@expliq.dev`. If found, it deletes that user's workspace and everything in it (automations, connector configs), then creates everything fresh. Simple, predictable — you always get a clean state. Downside: any manual edits you made in the UI (e.g., setting an owner on an automation) are wiped.

2. **Skip if exists**: The script checks if `seed-test@expliq.dev` exists. If so, it prints "Seed data already exists, skipping" and exits. You'd need to manually delete the workspace to re-seed. Simple but inflexible.

3. **Upsert each record**: The script updates existing records and creates missing ones. Most complex, but preserves manual edits. Overkill for a dev seed script.

**Recommendation:** Option 1 (delete-and-recreate). It's the simplest and most useful for development — when you want fresh seed data, you just run the script and get a clean slate. Manual UI edits during development are throwaway anyway. The script only touches the seed workspace (identified by the `seed-test@expliq.dev` email), so it never affects other workspaces.

### 9. LLM on Mock Data — Trade-off

You asked whether the mock workspace should also call the LLM. Here's the trade-off:

**Running LLM on mock automations:**
- (+) LLM-generated fields (name, description, trigger, etc.) would sound natural
- (-) Requires realistic `rawWorkflowJson` for each mock automation — significant authoring effort to write 15+ plausible n8n workflow JSONs
- (-) LLM will classify most as "high" impact (same problem as existing data — see epic 04 results), defeating the diversity goal
- (-) Non-deterministic — LLM output varies between runs, so seed data isn't stable
- (-) Costs ~$0.30 and takes ~3 minutes per seed run
- (-) `impactProposal` from LLM would need to be overridden with `impactOverride` anyway to get diversity

**Hardcoding all fields on mock automations (no LLM):**
- (+) Full control over every field — guaranteed diversity in impact, risk, owners, signals
- (+) Deterministic — same data every run
- (+) Instant — no API calls, no cost
- (+) `rawWorkflowJson` can be minimal (just needs valid JSON)
- (-) Need to write ~15 realistic-sounding names, descriptions, business contexts by hand

**Recommendation:** Don't run LLM on mock data. The whole point of the mock workspace is **controlled diversity** — specific impact levels, owner assignments, review dates, and governance signal combinations that produce all three risk levels. The LLM would fight against this by classifying everything as "high". Hardcode the LLM fields with realistic-sounding text (can borrow patterns from the epic 04 sample output). The real workspace already covers the "full LLM pipeline" scenario. Use minimal `rawWorkflowJson` for mocks.

### Proactive Flags

#### 1. Server Action Coupling — Hidden Implementation Concern

The spec says the real workspace should "run the existing sync pipeline (`syncWorkflows`)" and "run the existing LLM pipeline (`processUnprocessedAutomations`)". However, both are **server actions** that call `getRequiredSession()` — they cannot be called from a standalone script.

After investigating the code:
- `processAutomation(automationId, workspaceId)` in `src/lib/llm-pipeline.ts` is **directly reusable** — takes explicit params, no session dependency.
- `createN8nClient(instanceUrl, apiKey)` in `src/lib/n8n-client.ts` is **directly reusable** — pure HTTP client.
- `encrypt()` in `src/lib/encryption.ts` is **directly reusable**.
- But the **sync upsert logic** (iterate workflows, create/update automations, mark missing as removed) is embedded inside the `syncWorkflows` server action in `src/lib/actions/connector.ts` — it's NOT extracted as a standalone function.

**Recommendation:** The spec should clarify that the seed script reuses the **lower-level modules** (`n8n-client.ts`, `llm-pipeline.ts`, `encryption.ts`), not the server actions. For the real workspace sync, the script will need to replicate the sync upsert loop from `actions/connector.ts` (or the implementer can extract it into a shared function). This is a small amount of code (~30 lines of upsert logic) but should be explicit in the spec so the implementer isn't surprised.

oke

#### 2. No Cascading Deletes in Schema

The idempotency strategy says "deletes their workspaces and all dependent records." But the Prisma schema has **no `onDelete: Cascade`** on the Workspace → Automation, Workspace → ConnectorConfig, or Workspace → User relations. Deleting a Workspace directly would fail with foreign key constraint errors.

**Recommendation:** The spec should note that deletion must happen in dependency order: Automations → ConnectorConfigs → User → Workspace. This is an implementation detail, but since the spec calls out the idempotency strategy specifically, it should be accurate about how it works. Alternatively, add a note that the implementer should delete in the correct order or use a transaction.

oke

#### 3. Approximate Count (~15) Makes AC Untestable

The AC says "~15 non-removed automations" — the tilde makes it impossible to verify. Is 12 enough? Is 20 too many?

**Recommendation:** Pick a specific number. Based on the diversity requirements (4 impact levels × at least 2 each, 3+ owners, 5 governance signals, 3 risk levels, some multi-system, some sparse), **15** is a good target. Change "~15" to "at least 15" throughout the spec, giving the implementer flexibility to add more if needed for coverage but a clear minimum.

oke

#### 4. Idempotency AC Is Misleading Given LLM Non-Determinism

The AC says "running it twice produces the same result." But the LLM is non-deterministic — running twice will produce different names, descriptions, and potentially different impact classifications. The *structure* (number of automations, governance fields, removed status) will be the same, but the LLM-generated content will differ.

**Recommendation:** Reword to: "running it twice produces no duplicate records and no errors — the previous seed data is cleanly replaced." This captures the actual intent (idempotent cleanup) without implying deterministic output.

oke

#### 5. LLM systemsTouched May Override Hardcoded Governance Diversity

The spec says governance fields are "hardcoded on each mock automation." But `systemsTouched` is an LLM-generated field — the LLM pipeline writes to it. If the seed script hardcodes `systemsTouched` on mock automations and then runs the LLM pipeline, the LLM will **overwrite** `systemsTouched` with its own extraction from `rawWorkflowJson`. This means the system filter diversity depends on the mock workflow JSONs, not the hardcoded values.

**Recommendation:** Acknowledge that `systemsTouched` (and `triggerType`) come from the LLM, not from hardcoding. The mock workflow JSONs must be crafted to touch the desired systems. This is fine — it just means the mock workflow JSON design drives both impact classification AND system diversity. The spec's data design section should be updated to reflect this: system diversity comes from the mock workflows, not from hardcoded overrides.
